# Feature Specification: Things 칸반 프로젝트 초기 구성

**Feature Branch**: `001-initialize-project`
**Created**: 2026-07-30
**Status**: Draft
**Input**: User description: "GOAL.md를 참고하여 프로젝트 초기 코드 구성"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Things 할 일을 보드에서 파악하기 (Priority: P1)

Things 3 사용자는 앱을 열어 활성 할 일을 `To Do`와 `In Progress` 열에서 확인하고, 각 카드의 제목, 프로젝트 또는 Area, 일정, 주요 태그를 한눈에 파악한다.

**Why this priority**: Things를 원본으로 유지하면서 현재 작업량과 진행 상황을 시각화하는 것이 제품의 핵심 가치이며, 이후의 모든 상호작용이 이 읽기 흐름에 의존한다.

**Independent Test**: 여러 프로젝트, Area, 태그 및 일정 정보를 가진 활성 할 일을 준비한 뒤 앱을 열어 각 할 일이 정확한 열과 맥락 정보로 표시되는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 상태 태그가 없는 활성 할 일이 Things에 있을 때, **When** 사용자가 보드를 열거나 새로고침하면, **Then** 해당 할 일이 `To Do` 열에 표시된다.
2. **Given** `status:in-progress` 태그를 가진 활성 할 일이 있을 때, **When** 사용자가 보드를 조회하면, **Then** 해당 할 일이 `In Progress` 열에 표시된다.
3. **Given** 최근 완료된 할 일이 있을 때, **When** 사용자가 `Done` 열과 조회 기간을 활성화하면, **Then** 선택한 기간에 해당하는 완료 항목만 표시된다.
4. **Given** 사용자가 앱 밖에서 Things 데이터를 변경했을 때, **When** 앱이 다시 포커스를 얻거나 사용자가 새로고침하면, **Then** 보드가 Things의 최신 상태와 일치한다.

---

### User Story 2 - 카드 상태를 안전하게 변경하기 (Priority: P2)

사용자는 카드 드래그 앤 드롭 또는 키보드 조작으로 할 일의 상태를 바꾸고, 그 결과가 Things의 태그 또는 실제 완료 상태에 반영되었음을 확인한다.

**Why this priority**: 상태 변경은 읽기 전용 시각화를 실제 작업 흐름으로 확장하지만, Things 데이터 보존과 실패 복구가 보장된 뒤 제공되어야 한다.

**Independent Test**: 테스트 할 일을 각 열 사이로 이동하고 Things에서 태그와 완료 여부를 확인하며, 의도적으로 쓰기 실패를 발생시켜 원래 상태로 복구되는지 검증한다.

**Acceptance Scenarios**:

1. **Given** `To Do` 카드가 있을 때, **When** 사용자가 카드를 `In Progress`로 이동하면, **Then** 변경 중 상태가 즉시 보이고 Things 확인 후 `status:in-progress` 상태로 확정된다.
2. **Given** `In Progress` 카드가 있을 때, **When** 사용자가 카드를 `To Do`로 이동하면, **Then** 진행 상태 태그가 제거되고 다른 관련 태그와 PARA 소속은 유지된다.
3. **Given** 활성 카드가 있을 때, **When** 사용자가 카드를 `Done`으로 이동하면, **Then** Things의 실제 완료 상태로 기록된다.
4. **Given** 쓰기 또는 사후 검증이 실패할 때, **When** 상태 변경이 완료되지 못하면, **Then** 카드는 이전 열로 복구되고 원인과 재시도 방법이 표시된다.
5. **Given** 포인터를 사용할 수 없는 사용자가 있을 때, **When** 키보드로 카드 상태를 변경하면, **Then** 포인터 조작과 동일한 결과가 발생하고 변경 결과가 보조 기술에 전달된다.

---

### User Story 3 - 필요한 할 일만 찾아 집중하기 (Priority: P3)

사용자는 프로젝트, Area, 태그 필터와 제목 검색 및 정렬을 사용해 긴 목록에서 현재 필요한 작업만 좁혀 본다.

**Why this priority**: 핵심 보드와 상태 전이가 독립적으로 가치를 제공한 뒤, 실제 규모의 할 일 목록에서도 빠르게 집중할 수 있게 한다.

**Independent Test**: 서로 다른 프로젝트, Area, 태그 및 제목을 가진 할 일 집합에서 각 조건과 조합 조건을 적용해 일치하는 카드만 남는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 여러 프로젝트와 Area의 카드가 표시될 때, **When** 사용자가 특정 프로젝트 또는 Area를 선택하면, **Then** 해당 범위에 속한 카드만 표시된다.
2. **Given** 다양한 제목과 태그의 카드가 있을 때, **When** 검색어 또는 태그 필터를 적용하면, **Then** 조건에 맞는 카드와 열별 개수가 일관되게 갱신된다.
3. **Given** 필터 결과가 없을 때, **When** 보드가 결과를 표시하면, **Then** 오류 화면이 아니라 조건을 해제할 수 있는 빈 상태 안내가 나타난다.

---

### User Story 4 - Things에서 원본 확인하기 (Priority: P4)

사용자는 카드나 소속 정보를 선택해 Things의 해당 항목으로 이동하고 원본 세부 정보를 확인한다.

**Why this priority**: 이 앱이 Things를 대체하지 않고 보조한다는 원칙을 분명히 하며, 사용자가 원본으로 자연스럽게 돌아갈 수 있게 한다.

**Independent Test**: 식별 가능한 할 일과 소속 항목의 열기 액션을 실행해 Things가 올바른 원본 위치를 표시하는지 확인한다.

**Acceptance Scenarios**:

1. **Given** Things에서 식별 가능한 카드가 있을 때, **When** 사용자가 `Things에서 열기`를 실행하면, **Then** Things 앱에서 해당 할 일이 열린다.
2. **Given** 직접 이동을 지원하지 않는 항목이 있을 때, **When** 사용자가 열기 액션을 확인하면, **Then** 실행 불가능한 액션이 오해를 유발하지 않도록 비활성화되거나 이유가 안내된다.

### Edge Cases

- Things가 설치되지 않았거나 실행할 수 없는 경우 보드 대신 원인과 해결 방법을 제공한다.
- macOS 자동화 권한이 거부된 경우 읽기 가능 여부와 쓰기 불가 상태를 구분하고 권한 설정 방법을 안내한다.
- 동일한 할 일에 충돌하는 상태 태그가 있으면 임의로 덮어쓰지 않고 충돌을 표시하며, 사용자가 다음 상태를 선택할 때 하나의 유효 상태로 정규화한다.
- 외부 변경과 앱의 상태 변경이 겹치면 Things에서 다시 읽은 결과를 최종 상태로 삼고 불일치를 사용자에게 알린다.
- 할 일 식별자를 안정적으로 연결할 수 없으면 잘못된 항목을 갱신하거나 여는 대신 해당 작업을 중단하고 안내한다.
- 많은 활성 및 완료 항목이 존재해도 완료 조회는 선택한 최근 기간으로 제한하고, 긴 활성 목록에서 검색·필터 조작이 계속 가능해야 한다.
- 제목, 프로젝트, Area, 일정 또는 태그 일부가 비어 있어도 카드는 사용 가능한 정보만으로 표시된다.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 시스템은 Things의 활성 할 일을 읽어 완료 여부와 상태 태그에 따라 `To Do` 또는 `In Progress`로 분류해야 한다.
- **FR-002**: 시스템은 선택한 최근 기간의 완료 할 일을 사용자가 활성화한 경우에만 `Done` 열에 표시해야 한다.
- **FR-003**: 각 열은 현재 표시 조건에 해당하는 카드 수를 제공해야 한다.
- **FR-004**: 각 카드는 제목과, 존재하는 경우 프로젝트 또는 Area, 마감일, 예정일 및 주요 태그를 표시해야 한다.
- **FR-005**: 사용자는 드래그 앤 드롭과 키보드 조작 모두로 `To Do`, `In Progress`, `Done` 사이의 지원되는 상태 전이를 실행할 수 있어야 한다.
- **FR-006**: 시스템은 상태 변경 중임을 즉시 표시하고, 원본 확인이 성공한 후에만 변경을 확정해야 한다.
- **FR-007**: 시스템은 상태 쓰기 또는 검증 실패 시 표시 상태를 이전 값으로 복원하고 원인과 재시도 수단을 제공해야 한다.
- **FR-008**: 시스템은 앱 시작, 창 포커스 복귀 및 수동 새로고침 시 Things의 최신 상태를 다시 조회해야 한다.
- **FR-009**: 사용자는 프로젝트, Area, 태그별 필터와 제목 검색을 사용할 수 있어야 하며 조건을 조합할 수 있어야 한다.
- **FR-010**: 사용자는 보드 결과를 일정 및 제목 등 제공되는 주요 기준으로 정렬할 수 있어야 한다.
- **FR-011**: 사용자는 식별 가능한 카드에서 해당 할 일을 Things로 직접 열 수 있어야 한다.
- **FR-012**: 시스템은 로딩, 결과 없음, 권한 거부, Things 사용 불가, 읽기 실패, 쓰기 실패를 서로 구분해 표시해야 한다.
- **FR-013**: 시스템은 한 할 일에 하나의 상태 태그만 유효한 것으로 취급하고, 충돌 발견 시 사용자 선택 전까지 원본을 임의 수정하지 않아야 한다.
- **FR-014**: 초기 구성은 보드 조회, 상태 전이, 필터링, 원본 열기 및 오류 복구 흐름을 서로 독립적으로 검증할 수 있는 경계를 제공해야 한다.
- **FR-015**: MVP는 Things를 대체하는 독립 데이터 관리, 클라우드 직접 통신, 다중 사용자 협업, 임의 개수의 워크플로 열 및 독자적인 카드 순서 저장을 제공하지 않아야 한다.

### Things Integration and Safety *(mandatory when Things data is read or written)*

- **TI-001**: 할 일·프로젝트·Area·태그·완료 항목 조회와 변경 후 확인은 읽기 작업이며, 상태 태그 변경·완료·완료 취소는 쓰기 작업으로 명시적으로 구분해야 한다.
- **TI-002**: 모든 쓰기는 지원되는 AppleScript 또는 Things URL 동작으로만 수행해야 하며, Things 데이터 저장소에 직접 쓰는 행위는 금지한다.
- **TI-003**: 모든 변경은 이전 상태, 목표 상태 및 대상 식별 정보를 기준으로 수행하고, 완료 후 Things에서 다시 읽어 확인하며, 실패 시 표시 상태를 이전 상태로 롤백해야 한다.
- **TI-004**: 자동화 권한 거부, Things 사용 불가, 충돌 상태 태그 및 외부 변경을 각각 식별 가능한 상태로 처리하고 사용자가 취할 수 있는 조치를 안내해야 한다.
- **TI-005**: 상태 변경은 대상 상태 표현에 필요한 정보만 수정하고, 관련 없는 태그, 메타데이터, 프로젝트 및 Area 소속을 보존해야 한다.
- **TI-006**: Things는 할 일과 완료 상태의 유일한 원본이어야 하며, 앱은 별도의 독자적인 할 일 사본이나 완료 상태를 영구 보관하지 않아야 한다.
- **TI-007**: 진단 정보에는 할 일 본문이나 민감한 메모를 기본적으로 포함하지 않아야 한다.

### Accessibility Requirements *(mandatory for interactive UI)*

- **AR-001**: 모든 드래그 앤 드롭 상태 변경은 키보드로도 동일하게 수행할 수 있어야 한다.
- **AR-002**: 로딩, 빈 상태, 성공 및 실패 상태는 색상에만 의존하지 않고 인지 가능해야 한다.
- **AR-003**: 카드의 현재 상태, 이동 가능한 대상 및 상태 변경 결과가 보조 기술 사용자에게 전달되어야 한다.
- **AR-004**: 주요 보드, 필터, 새로고침 및 원본 열기 기능은 논리적인 키보드 탐색 순서로 접근 가능해야 한다.

### Key Entities *(include if feature involves data)*

- **Todo**: Things의 할 일을 나타내며 식별 정보, 제목, 완료 여부, 마감일, 예정일, 프로젝트 또는 Area, 태그를 가진다.
- **Project**: 관련 할 일을 묶는 완료 기준이 있는 Things 단위로, 이름, 식별 정보, 소속 Area 및 활성 여부를 가진다.
- **Area**: 지속적으로 관리하는 책임 영역이며 프로젝트와 할 일의 PARA 맥락을 제공한다.
- **Tag**: 할 일의 분류 정보이며 상태 태그와 기타 사용자 태그를 구분할 수 있다.
- **Kanban Status**: 보드에서 파생된 `To Do`, `In Progress`, `Done` 상태로, Things의 상태 태그 또는 실제 완료 여부에 대응한다.
- **Status Mapping**: 각 칸반 상태가 Things의 어떤 원본 표현과 연결되는지를 정의한다.
- **Board View**: 검색어, 프로젝트·Area·태그 필터, 정렬 기준, 완료 열 표시 여부와 완료 조회 기간으로 구성된 현재 조회 조건이다.
- **Status Transition**: 대상 할 일, 이전 상태, 목표 상태, 검증 및 복구 결과를 포함하는 한 번의 사용자 변경 요청이다.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 사용자는 앱 실행 후 5초 이내에 첫 활성 할 일 목록 또는 조치 가능한 연결 안내를 볼 수 있다.
- **SC-002**: 대표 데이터 집합의 활성 할 일 100%가 완료 여부와 상태 태그 기준에 맞는 열에 표시되고 프로젝트·Area 및 태그 맥락을 보존한다.
- **SC-003**: 정상 환경에서 실행한 상태 변경의 100%가 3초 이내에 성공 확인 또는 명확한 실패·복구 결과를 제공한다.
- **SC-004**: 실패가 주입된 상태 변경 시 100%의 카드가 원래 표시 상태로 돌아가며 Things의 관련 없는 데이터가 변경되지 않는다.
- **SC-005**: 사용성 검증 참가자의 90% 이상이 별도 도움 없이 보드 조회, 카드 상태 변경, 필터 적용 및 Things에서 열기를 완료한다.
- **SC-006**: 키보드 전용 검증에서 핵심 상태 전이 시나리오의 100%를 완료할 수 있고 현재 상태와 결과를 비시각적으로 확인할 수 있다.
- **SC-007**: 외부에서 변경한 대표 시나리오의 100%가 수동 새로고침 또는 포커스 복귀 후 5초 이내에 보드와 일치한다.
- **SC-008**: 자동화 권한 거부, Things 사용 불가, 읽기 실패 및 쓰기 실패의 각 검증 시나리오에서 사용자가 원인과 다음 행동을 구분할 수 있다.

## Assumptions

- 초기 구성의 목표는 GOAL.md에 정의된 MVP 사용자 흐름을 구현·검증할 수 있는 프로젝트 기반과 첫 실행 가능한 제품 골격을 마련하는 것이다.
- 대상 사용자는 Things 3가 설치된 macOS 환경에서 자신의 로컬 Things 데이터를 다루는 단일 사용자다.
- MVP 상태 태그는 `status:in-progress`를 사용하며, 상태 태그가 없는 활성 할 일은 `To Do`로 간주한다. `status:todo`는 호환 가능한 명시적 표현으로 취급할 수 있다.
- `Done`은 별도 태그가 아니라 Things의 실제 완료 여부로 판단하며 기본 보드에서는 선택적으로 표시한다.
- 새 할 일 생성과 상태 태그 이름 사용자 설정은 초기 구성 범위 밖이며, 향후 추가 시 기존 프로젝트 또는 Area 배치를 강제한다.
- 완료 항목의 기본 조회 기간과 구체적인 정렬 우선순위는 계획 단계에서 합리적인 데스크톱 기본값으로 정하되 사용자가 변경할 수 있어야 한다.
- Things 연동 방식별 식별자 호환성은 구현 초기에 검증하며, 안정적인 대상을 식별할 수 없는 작업은 안전하게 비활성화한다.
